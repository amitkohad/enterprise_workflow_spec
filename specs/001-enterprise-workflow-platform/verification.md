# Verification and release acceptance

**Feature:** `001-enterprise-workflow-platform`  
**Status:** executable test requirements for generated implementation; no application tests have been run by this specification task.  
**References:** [spec.md](spec.md), [plan.md](plan.md), [operations.md](operations.md), and [tasks.md](tasks.md).

Every implementation task must identify its applicable verification IDs, smallest test command and objective pass condition. Favor tests of externally meaningful contracts, recovery boundaries and deterministic behavior. Mock assertions that merely mirror a function's statements do not establish correctness. A required test that cannot run is reported as blocked with its reason, never passed or silently skipped.

## 1. Test layers and execution environments

| Layer | Environment | What it can establish | What it cannot establish |
|---|---|---|---|
| Unit/contract | Python/pytest with controlled settings, clocks and SDK/broker interfaces | Validation, envelopes, cryptography, identity mapping, bounded state machines, interceptors and typed errors | Real Temporal/Kafka durability, TLS enforcement or Kubernetes operation |
| Workflow | Temporal `WorkflowEnvironment.start_time_skipping()` and real SDK workers | Deterministic workflow logic, timers/retries, activity stub integration, cancellation and payload converter round trips | Broker behavior, production throughput, real server mTLS/authorization or cluster probes |
| Local integration | `WorkflowEnvironment.start_local()` or disposable real Temporal, real Kafka/TLS test broker and HTTP server | Server histories, client/worker converter compatibility, actual offsets/delivery, protocol behavior and TLS negatives | Enterprise quotas, actual cluster CNI, production availability |
| Replay | `Replayer` with representative encrypted histories and compatible codec/keys | New workflow code compatibility with recorded decisions | Future histories not represented by corpus or downstream side-effect correctness |
| Kubernetes/staging | Same built image and rendered production config on supported cluster, real dependency endpoints | Probes, signal handling, networking, KEDA, resource bounds, rollouts and workload qualification | Universal capacity guarantees beyond recorded topology/workload |

Temporal time skipping fast-forwards timers when activities are not running, and the test server's clock is shared across workflows in an environment. Isolate environments for incompatible clock modes and avoid relying on wall-clock durations in time-skipping tests. Use a real non-skipping environment for elapsed-time, heartbeat, shutdown and load checks. [Temporal Python testing suite](https://docs.temporal.io/develop/python/best-practices/testing-suite)

Provision external integration dependencies through a documented CI service or disposable test configuration. Pin test server/broker binaries or images and record download/provisioning requirements; do not download them silently during every test. Run integration jobs on a supported SDK test-server platform and report unsupported local platforms explicitly. Test credentials are disposable synthetic secrets injected at runtime. The production application image never contains fixture keys or test-server binaries.

## 2. Test data, evidence and fixtures

- Use synthetic PII markers with known byte strings in input, output and failing paths. Raw data is permitted only inside isolated test memory and protected disposable test Kafka topics; production artifacts and logs must remain free of it.
- Fixtures identify schema/codec/workflow versions, expected namespace/route, expected encryption key ID, and whether the workflow is open/closed. Never check in a production history unchanged. Generate representative histories from synthetic workflows, then encrypt them using dedicated CI fixture keys supplied separately.
- Sanitize IDs, plaintext metadata, failure messages and headers before retaining fixtures. Keep ciphertext intact; arbitrary edits to history decisions can invalidate replay. CI artifact access/retention policy treats histories as sensitive even when payloads are encrypted.
- A release report records git revision, image digest, Python/SDK/broker/server/KEDA/Kubernetes versions, exact commands, environment configuration without secrets, pass/fail/blocked results, timestamps, sample counts and links to controlled evidence.
- Unit, workflow and replay gates run on every change. Real integration gates run for the main branch/release and for changes touching security, clients, ingestion, activities, lifecycle or delivery semantics. Full staging qualification runs before the first production release and after material concurrency/routing/SDK/codec/scaling changes.

## 3. Verification catalog

### Configuration, cryptography and transport

| ID | Minimum executable case | Objective acceptance |
|---|---|---|
| **V-001** | Instantiate both roles with valid production config; vary missing cert/key/CA/keyring, invalid role, wildcard/unregistered route, more than16 selected namespace clients/consumer bindings, more than4 selected worker queues, worker namespace mismatch, insecure Kafka/TLS option and unsafe dev override | Production startup rejects every invalid case with safe typed diagnostic before accepting traffic/polling; valid settings produce exactly the bounded selected registered map and path-only mounted credential profiles |
| **V-002** | Encode/decode a sequence containing empty, nested, Unicode, binary and typed payloads using the SDK converter in two independently constructed codec instances | Byte-exact payload/protobuf metadata restoration; equal plaintext encodes differently across repeated invocations; envelope includes supported version/key ID and expected authenticated framing; encode/decode return SDK `Payload` objects |
| **V-003** | Mutate nonce, ciphertext, tag, authenticated version/key ID/framing; truncate envelope; use unknown key, wrong key, malformed payload and unexpected plaintext in production | Every corrupted/unsupported envelope fails closed without plaintext fallback, key material, business values or raw exception contents leaking; finite size limits reject oversized input |
| **V-004** | Reader with old+new keyring reads old ciphertext; separately constructed ingress/worker/replayer readers exchange new ciphertext; reader lacking old key reads old history | Supported readers decode both writers; missing/retired key fails explicitly; rotation never rewrites old ciphertext or silently substitutes another key |
| **V-005** | Run actual client-to-worker encrypted workflow with synthetic markers in input/result, activity input/result, memo, heartbeat details and a controlled failure; fetch raw history and pending-activity describe or heartbeat-timeout last_heartbeat_details without business decode | Markers absent from raw payload/memo/heartbeat bytes and visible metadata/failure strings/logs; identity memo demonstrably encrypted and request digest never logged; headers/search attributes follow privacy allowlist; authorized gateway decodes result; failure converter policy verified separately from payload codec |
| **V-006** | Connect production Temporal client to actual TLS server with valid credentials, missing cert, mismatched private key, expired cert, untrusted CA, wrong server hostname and unauthorized namespace; equivalent trusted/untrusted Kafka TLS cases | Only authorized validated connections work; no downgrade/hostname bypass; client/worker settings enforce the same security policy; certificates and keys not printed in diagnostics |

V-002 is a probabilistic uniqueness smoke test, not a mathematical proof of nonce safety. Review the nonce generation/key management construction separately. V-005 checks the application's privacy boundary, not a claim that Temporal workflow IDs/search metadata, Kafka source values or third-party telemetry are universally encrypted. Negative transport cases require a server that enforces the intended TLS/authorization policy; a mock connection object does not satisfy V-006.

### Authentication, routing and REST contracts

| ID | Minimum executable case | Objective acceptance |
|---|---|---|
| **V-007** | Valid OIDC bearer; no token; invalid signature/algorithm/issuer/audience; expired/not-yet-valid token; absent tenant or missing permission; unknown JWKS key; key refresh unavailable with and without valid cached key | Valid principal succeeds; invalid/unauthorized principal receives specified 401/403 with safe error; unknown key causes bounded refresh then rejection; no HTTP/Temporal start occurs before authorization |
| **V-008** | Four tenant namespaces/routes; attempt cross-tenant status lookup, forged tenant body/header, arbitrary namespace/queue/topic/workflow type; test broker topic identity mapping | Tenant claim and configured trusted broker route determine namespace/queue/type; unauthorized access does not disclose existence/result; ingress and worker maps agree and never create dynamic queues/clients |
| **V-009** | Retry same tenant/idempotency key/body concurrently across two ingestion instances; same key with changed body/route; duplicate active and closed workflows; same key across isolated tenants; ambiguous start timeout after durable accept | Exactly one eligible execution in the retained identity window; approved duplicate returns existing identity without waiting for completion; mismatched identity metadata is rejected; ambiguity retry reuses same identity; no process-local cache is required for correctness |
| **V-010** | Query running/completed/failed/cancelled/timed-out/missing workflow; completed decoded result; large result; request during worker absence; unavailable Temporal | Status endpoint remains bounded and nonblocking for running workflows; returns specified terminal result/error representation only to authorized tenant; safe sizes/deadlines and typed upstream errors enforced |

REST identity tests must observe raw Temporal execution count/run history, not only two HTTP responses. Closed-history identity rejection is limited by Temporal retention; explicitly exercise/document the behavior once a history is no longer retained. API start latency excludes workflow completion, and a workflow can be accepted while compatible workers are temporarily unavailable.

### Kafka consumption, recovery and downstream delivery

| ID | Minimum executable case | Objective acceptance |
|---|---|---|
| **V-011** | Valid keyed event; absent/empty/oversized/noncanonical key; Message_ID/key mismatch; unknown schema/route; invalid JSON/PII-bearing error; trusted tenant mapping violation | Message identity and trust boundary follow event contract; permanent bad record goes through metadata-only DLQ disposition; transient errors are retried uncommitted; raw values never enter logs/DLQ |
| **V-012** | Real broker and Temporal: kill ingestion after durable start acknowledgment before source commit; restart with same group and same route config | Source redelivers; retained Temporal identity verifies the existing execution; exactly one eligible workflow execution; offset commits only after acknowledgment/verification; downstream workflow completion is not awaited |
| **V-013** | Interleaved partitions and unresolved earliest record; force commit RPC failure and lost response; later cross-partition successes | Per-partition commit offset equals next offset after contiguous acknowledged fence; never skips unresolved record; failed/ambiguous commit leads to safe redelivery; other partitions make progress within bounded concurrency |
| **V-014** | Scale group up/down during in-flight Temporal starts; revoke partition; simulate lost ownership; delay completion until new assignment generation | Obsolete completion cannot commit; current owner recovers source record; acknowledged duplicates remain safe; consumer continues polling within configured interval; no offset skips during repeated rebalances |
| **V-015** | Invalid record; unavailable DLQ; DLQ broker acknowledgment followed by crash before source commit; recovery | No source commit before DLQ acknowledgment; possible redelivery creates deterministic duplicate DLQ identity rather than loss; safe metadata only; original source record remains recoverable through configured retention |
| **V-016** | Fill command/completion queues across multiple selected bindings, stall Temporal and Kafka, keep API/probes under load, then recover; inject one broker-thread fatal exception | At most16 consumer threads,32 global Kafka-admitted starts,256 global buffered source records and 16 namespace clients; separate bounded REST admission; one unresolved start per partition; bounded memory; consumers pause/resume without losing poll progress; event loop responsive; fatal thread error triggers coordinated role shutdown/nonzero exit |
| **V-017** | Actual `publish_event` activity: producer acknowledgment then kill worker before activity completion; retry on new worker with new producer; fail delivery and producer queue capacity | Activity succeeds only after acknowledged delivery; retry may produce duplicates but every copy shares `<workflow_id>:publish:0`; `workflow.processed` is emitted before workflow completion and result includes receipt; downstream test sink deduplicates by event ID |
| **V-018** | ActivityEnvironment for heartbeat details/cancellation; non-skipping integration with long delivery wait, heartbeat timeout, graceful shutdown and forced cancellation | Heartbeats occur while useful waiting/progress happens; configured heartbeat timeout is meaningful; activity stops on cancellation/shutdown and does not claim delivery without acknowledgment; no event-loop blocking publish/flush |

Kafka/Temporal coordination is at least once, not a cross-system exactly-once transaction. V-012 and V-015 need deterministic failpoints enabled only for testing so the vulnerable boundary is reliably exercised. V-013 can primarily test the acknowledgment state machine with controlled completions, but must include a real offset integration case. Never delete/reset the consumer group to make a failed recovery assertion pass. Producer idempotence alone is insufficient for V-017.

### Workflow correctness, replay and observability

| ID | Minimum executable case | Objective acceptance |
|---|---|---|
| **V-019** | WorkflowEnvironment with separate codec instances on starter/worker; successful reference workflow, transient activity retry, permanent failure, cancellation, timer and schema rejection | Reference workflow schedules its bounded activity with explicit deadlines/retry policy, publishes receipt/result on success and follows specified failure behavior; actual SDK conversion occurs; no direct broker/HTTP/time/random I/O in workflow code |
| **V-020** | Replay open and closed synthetic encrypted histories for every registered workflow/route and supported old schema/key/code branch; add intentionally nondeterministic mutation as negative control | Correct implementation replays all approved corpus without nondeterminism; negative control fails; replayer uses compatible converter/keyring and read-only replay cannot emit Kafka/API side effects |
| **V-021** | Concurrent tenant activity/workflow invocations, retries/failures and replay; capture structured logs; scrape both roles; interrupt collector | Expected execution context binds and resets correctly; replay-aware logs/metrics avoid duplicate application events; no PII/secret/high-cardinality labels; ingestion app metrics8080 present, worker app 8080 and SDK 9090 distinct; export failure does not block deterministic workflow progress |

CI must cover the actual sandboxed workflow registration/import path. Static scanning can support review but does not replace SDK execution. Replay tests use the selected converter and sanitized encrypted histories, with old fixture keys available through controlled CI secret injection. Collect representative new histories before approving a workflow change. Temporal recommends representative history replay in CI and failure on replay errors. [Temporal replay guidance](https://github.com/temporalio/sdk-python#workflow-replay)

V-021 distinguishes logical workflow elapsed duration from wall-clock activity duration; workflows use deterministic SDK time, activities may use a monotonic wall clock. Worker logs must have workflow/run/activity identifiers when applicable; metrics must not use those identifiers as labels. SDK exporter units/prefixes and registration count are asserted from the actual pinned SDK.

V-026 is a qualification gate with declared resources and quotas. It does not assert arbitrary enterprise workloads will meet the same targets. Maintain precise metric interval definitions from operations; Kafka local consume-to-start is not source-to-start latency, API status retrieval is not execution completion, and schedule-to-start histograms are not backlog size. Measure per-route percentiles with sufficient samples and report missing samples as unknown rather than zero. The SDK documents the schedule-to-start and slot metrics used here. [Temporal SDK metrics reference](https://docs.temporal.io/references/sdk-metrics)

## 4. CI gates and commands contract

The generated project must expose stable commands or documented pytest marker equivalents for these gates:

1. **Static/package gate:** dependency lock resolution, lint/type checks for touched code, syntax/import validation, secret scan, container vulnerability policy and manifest validation. Fail unsafe production configuration examples.
2. **Fast unit/contract gate:** V-001 through V-004; unit portions of V-007 through V-011, V-013 through V-018 and V-021/V-022. Complete without real services; no hidden network dependence.
3. **Workflow/replay gate:** V-019, V-020 and converter/interceptor portions of V-005/V-021. Fail if test server is unavailable; provide separately provisioned binary/image instructions.
4. **Real integration gate:** V-005/V-006, actual auth/start/status/routing paths V-007 through V-010, delivery/rebalance/crash portions V-011 through V-018, and actual lifespan/exporter checks V-021/V-022.
5. **Staging release gate:** V-023 through V-029 against the built image and production-equivalent config. Run V-026 before and after material tuning; record each revised parameter. Final V-030 checks the handoff.

Define markers `unit`, `workflow`, `replay`, `integration`, `kubernetes`, `load` and `chaos`; tasks may select narrower node IDs to keep feedback short. Provide timeout/cleanup behavior for every external-server test, unique consumer groups/workflow IDs where identity reuse is not the behavior under test, and deterministic artifact cleanup that never touches production namespaces/topics. Parallel execution must not share a time-skipping clock or reset a shared consumer group unexpectedly.

Coverage is a supporting signal; the acceptance catalog is the gate. A high line-coverage percentage cannot substitute for crash-boundary, replay, TLS-negative or tenant-isolation evidence. Keep the smallest test that detects a real contract violation, then integrate only the boundary it cannot establish.

## 5. Qualification procedure and recorded decisions

1. Record versions, image digest, route/namespace/topic maps, encrypted input limits, broker partitions/retention, pod requests/limits, slots/pollers, client/broker queues, ingress limits, service quotas and network profile. Record the controlled mechanism for approximately one-second activity execution and verify its actual duration; do not equate a one-second workflow timer with activity slot occupancy.
2. Verify required metrics/scaler queries with live zero, nonzero and absent-series cases. Warm up for a declared interval without including startup artifacts in steady-state percentiles; report startup separately.
3. Run steady mixed load and the independent REST/Kafka variants. Reconcile submitted event IDs, accepted starts, approved duplicates, rejected records, committed offsets, workflow outcomes and published event IDs.
4. Run the burst; report peak lag, replicas and task slots, earliest scaling decision, pod readiness delay, time to drain and any temporary rejection. Do not claim a 30-second polling setting guarantees 30-second recovery.
5. Execute outage/crash/rebalance/roll/key-rotation cases with declared failpoints and bounded cleanup. Confirm recovery and replay after each scenario before moving to the next.
6. Record pass/fail/blocked per V-ID, attach evidence and tune only with an explanation of the observed bottleneck. Repeat only the affected and required dependent gates after a change.

Release acceptance requires product behavior, confidentiality, tenant isolation, replay/delivery integrity and lifecycle gates to pass. Performance targets require a passing qualification report or an explicit revised capacity scope approved through the enterprise release process. The specification itself supplies no deployment approval, benchmark result or production availability certificate.
