# Deployment and operations contract

**Feature:** `001-enterprise-workflow-platform`  
**Application:** `temporal-enterprise-framework`  
**Document status:** implementation requirements; deployment has not been executed.  
**Documentation reviewed:** 2026-10-01. Upstream links describe the reviewed behavior; implementation must pin and qualify its dependency versions.

This document specifies how to deploy and operate the single application described in [spec.md](spec.md). Its requirements and [verification.md](verification.md) are release acceptance inputs, not evidence that a production installation already meets them. Temporal Service, Kafka, OIDC, ingress, Prometheus, Kubernetes, KEDA, and enterprise key/secret provisioning are external dependencies with named owners. The repository produces one image and runs exactly two container roles. Development-only dependency containers do not become additional application services.

## 1. Deployable unit and responsibility boundaries

| Concern | Required deployment behavior | Owner |
|---|---|---|
| Artifact | One immutable image digest, one locked Python dependency set, one entry point `python -m app.main` | Application team |
| Ingestion | Deployment with `APP_ROLE=INGESTION`; FastAPI and Kafka consumption share one process and supervised lifecycle | Application team |
| Execution | One or more Deployments with `APP_ROLE=WORKER`; same image, explicit namespace/queue/registration configuration | Application team |
| Temporal | Preprovisioned namespaces, retention, quotas, server identity, certificate authorization, availability and backups | Temporal platform owner |
| Kafka | Trigger/output/DLQ topics, partitions, retention, ACLs, TLS, consumer-group quotas and broker availability | Event platform owner |
| Authentication | Trusted OIDC issuer, audience, tenant claims, signing keys, token issuance and rotation | Identity owner |
| Secrets | Mounted Temporal credentials, Kafka credentials and payload keyring, provisioned by enterprise secret/KMS integration | Security/platform owner |
| Infrastructure | Namespace, ingress TLS, CNI policy enforcement, monitoring, KEDA and cluster capacity | Kubernetes platform owner |

No application database, codec web service, UI, third container role, dynamic plugin loading, or Temporal/Kafka control plane is introduced. Durable execution state lives in Temporal and Kafka offsets. Process caches and queues are bounded and disposable. If the enterprise requires deduplication beyond Temporal history retention, it must provide a separately approved design; this release does not invent a durable deduplication store.

`INGESTION` runs exactly one Uvicorn process per pod, without reload or an ASGI multiprocess manager. Creating Kafka consumers during import or once per HTTP request is forbidden. FastAPI lifespan creates the namespace client pool, consumer bridge and supervisor once. A fatal consumer/HTTP supervisor error marks the pod unready, initiates joint shutdown, and returns a nonzero exit code. Temporary dependency errors use bounded retry and degraded readiness rather than an unbounded restart loop.

Each `WORKER` pod binds to one configured Temporal namespace and no more than four allowlisted queues. Worker deployments may be repeated for additional namespaces or capacity pools using the same image. The ingestion pool permits no more than sixteen configured namespace clients, all on the configured Temporal endpoint with tenant-specific mounted credential profiles authorized for precisely their namespaces. Invalid maps, unknown workflow registrations, wildcard queues and unbounded client creation fail startup. These are application design limits and are not Temporal platform limits.

## 2. Required Kubernetes deliverables

The implementation must provide renderable deployment configuration with a production values example containing placeholders, never credentials. A chart or Kustomize arrangement is acceptable if [plan.md](plan.md) selects one and documents its command. Its rendered production resources must include:

- Separate `INGESTION` and `WORKER` Deployments referencing the same image digest; explicit role/config values, configuration checksum annotations and read-only secret mounts.
- Ingestion ClusterIP Service on application port 8080 and TLS ingress exposing only public `/v1` API paths. Ingress request size, timeout and rate limits align with API settings. Worker has no public API ingress.
- Internal application monitoring/probe access on 8080 for both roles; worker SDK scrape access on 9090. Separate scrape targets and jobs must avoid double counting.
- One ServiceAccount per role with `automountServiceAccountToken: false`, and no Kubernetes API permissions by default. A narrowly scoped projected identity is an enterprise integration exception only when explicitly configured.
- Role-specific NetworkPolicies, PodDisruptionBudgets, resource requests/limits, topology distribution, configuration/secret references, and one KEDA ScaledObject per autoscaled Deployment.
- A startup probe, readiness probe and liveness probe on application port 8080. Neither metrics endpoint is a probe target.

Production minimum replica count is two for ingestion and two for every active worker deployment. Use `maxUnavailable: 0`, `maxSurge: 1` for INGESTION rolling deployment and unchanged-code Worker certificate/key/config restarts. PINNED Worker code versions coexist in distinct immutable Kubernetes Deployments or Helm releases named by deployment/build identity; replacing the image in the old version's Deployment is forbidden. A qualified `COMPATIBLE_ROLLING` exception may use a replay-compatible in-place code rollout. A PDB with `minAvailable: 1` is a starting voluntary-disruption policy for a two-replica pool; its desired protection must be reconsidered for larger pools. Spread replicas across nodes and, where cluster capacity permits, zones. Missing topology capacity must produce a clear scheduling failure rather than silently asserting availability. Kubernetes PDBs constrain voluntary disruptions; they do not protect against every failure. [Kubernetes disruptions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)

Set non-root user/group IDs, `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, `seccompProfile.type: RuntimeDefault`, and drop all Linux capabilities. Provide a size-limited writable temporary `emptyDir` only for justified runtime needs. No host networking, host mounts, privileged container, writable credential mount or root permission workaround is acceptable. The image must run correctly with these restrictions. [Kubernetes restricted Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/)

Declare requests/limits for both CPU and memory; do not assume that worker concurrency translates directly into CPU allocation. Initial qualification may start with ingestion requests of 500 millicores/512 MiB and worker requests of 1 CPU/1 GiB, with configurable limits of 2 CPU/1 GiB and 4 CPU/2 GiB respectively. These are starting experiments, not capacity promises. Record CPU throttling, memory growth, replay cache behavior, queue sizes and measured per-pod capacity before selecting production values.

Worker limits are process-wide budgets: 32 Workflow Task slots, 64 Activity slots and 1000 cached workflows across the selected one to four queues. The producer wait budget is 64 across that process. Allocate finite positive per-queue limits whose sums do not exceed those budgets; if the pinned SDK has no process-wide limiter, configure explicit allocations rather than multiplying a default 64 by every queue. A shared executor of at most32 threads supports approved synchronous Activity extensions only; it does not multiply these task budgets.

## 3. Health, readiness and lifecycle

The application provides `/health/live`, `/health/ready` and `/health/startup` on 8080 for both roles. Responses contain only the bounded status values in the API contract: live `ok`, ready `ready`/`not_ready`, and startup `started`/`starting`. Internal health maintains dependency states and non-sensitive reason codes; public response bodies contain no exception text or certificate paths. Endpoints do not synchronously call external services on every probe; a supervised health loop maintains recent bounded observations.

| Probe/state | INGESTION | WORKER |
|---|---|---|
| Startup succeeds | Settings/keyring/certificates validated, routes bound, HTTP supervisor and broker bridge initialized, Temporal connection established, Kafka subscribe initiated | Settings/keyring/certificates validated, namespace connected, all registered queue workers initialized, SDK exporter bound |
| Ready | Not draining; consumer loop/bridge is healthy and within progress bound; Temporal and Kafka recent checks successful; auth key cache usable | Not draining; worker supervisor healthy; Temporal connectivity recent and all configured workers initialized |
| Live | Process/event loop and supervisor remain responsive | Process/event loop and supervisor remain responsive |
| Remote outage | Become unready after bounded health failure threshold, retain live state and retry | Become unready after bounded health failure threshold, retain live state and let SDK reconnect |
| Fatal internal failure | Joint teardown and nonzero exit | Joint teardown of HTTP monitor and every worker; nonzero exit |

A healthy Kafka consumer with no assigned partitions is permitted when replicas exceed partitions for REST capacity. Empty topics and idle Temporal queues are healthy; task completion is not required to pass readiness. A partition blocked by a poison record has a visible degraded partition state and alert; it does not trigger endless process restarts. Readiness is conservative for the coupled ingestion role: a Kafka outage also removes API traffic from that pod, an explicit availability tradeoff of the two-role design.

Starting probe values are startup every 5 seconds with 24 failures allowed, readiness every 5 seconds with 3 failures allowed, and liveness every 10 seconds with 3 failures allowed. Check timeout is 2 seconds. Startup prevents readiness/liveness checks during initialization; liveness is reserved for process failure. Tune values from qualification and document every change. [Kubernetes probe behavior](https://kubernetes.io/docs/concepts/workloads/pods/probes/)

`terminationGracePeriodSeconds` is 120 for both roles. Signal handling starts an overall 110-second application shutdown deadline, preserving Kubernetes termination headroom; `preStop` sleeps must not consume that budget. Kubernetes includes lifecycle-hook time in the termination grace period. [Kubernetes pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)

Ingestion shutdown must: mark unready; reject new starts; stop admitting new Kafka records while preserving polling/rebalance processing; finish or abandon in-flight starts within deadlines; commit only acknowledged contiguous offsets still owned by the current assignment; close the consumer on its owning thread; flush the producer within its bounded deadline; stop HTTP and join the broker thread. Work not known to be durably acknowledged remains uncommitted for redelivery. A locally timed-out Temporal start is ambiguous; redelivery uses the same workflow identity.

Worker shutdown must mark unready, stop polling through SDK shutdown, give activities a 90-second graceful window, honor activity shutdown/cancellation, close publishers/HTTP monitoring within the overall deadline, and release clients/runtime resources. Both roles must drain the qualification workload within 90 seconds; the 110-second hard process deadline covers forced cancellation/cleanup of exceptional work. Cancellation-resistant activity code must fail qualification. SDK shutdown waits for activities to finish, so setting a graceful timeout alone does not guarantee process exit. [Temporal Python worker shutdown](https://github.com/temporalio/sdk-python#worker-shutdown)

## 4. Kafka execution and commit operations

Select no more than sixteen consumer bindings per ingestion process; each binding has its own configured tenant topic, group and credential profile. Each selected consumer owns one dedicated broker I/O thread with bounded command/completion queues. Consumer creation, poll, subscription, pause/resume, offset operations, rebalance callbacks and close stay on its owning thread. Async code sends commands through bounded bridges; it never blocks the event loop on poll, commit, flush or a producer delivery callback. Kafka-admitted starts are capped globally at 32 and total buffered source records at 256 across all bindings, with one unresolved start per partition; smaller per-binding bounds may be configured. REST admission has its own finite configured limit. Producer polling/delivery callbacks must also have an explicitly owned bounded executor/bridge. Queue fullness applies backpressure; it must not allocate a task for every fetched record. The full routing inventory may contain more tenants than one process selects, but selection never bypasses these runtime bounds.

Disable automatic commits and automatic offset storage. An offset is eligible only after the Temporal start is acknowledged or an approved duplicate is verified, or after metadata-only DLQ delivery is acknowledged for a permanently invalid input. Offset `N+1` commits processing through `N`. Maintain a contiguous acknowledgment fence per partition and assignment generation; a later successful record never skips an earlier unresolved record. Per-partition start admission is ordered; cross-partition concurrency is bounded. Confluent documents manual offset management as the basis for application-controlled processing guarantees. [Confluent Python client offset management](https://docs.confluent.io/kafka-clients/python/current/overview.html)

On revoke, pause admission, drain within the rebalance deadline and commit only valid owned fences; on lost ownership, do not commit. Any completion tagged with an obsolete assignment generation is fenced out. Continue broker polls during Temporal retry and backpressure so group membership remains valid. Configure client/broker protocol and `max.poll.interval.ms` explicitly for the pinned Confluent version; test them against the deployed broker. Do not silently switch to an experimental consumer protocol.

Start acknowledgment followed by a crash before commit may cause another start attempt; Temporal identity/policy makes it a verified duplicate within the documented retention boundary. There is no distributed transaction between Temporal and Kafka. Publishing `workflow.processed` happens as an activity before workflow completion and returns its delivery receipt. A crash after broker acknowledgment but before activity completion may publish the event again; use event identity `<workflow_id>:publish:0`, and require downstream deduplication. Kafka producer idempotence does not prevent duplicates across activity retries or producer restarts.

DLQ records include only safe error codes, source topic/partition/offset, approved tenant/route identifiers and opaque correlation identifiers. Never include source value, raw business headers, JWT, decrypted payload or exception text. If DLQ delivery fails, do not commit the trigger record. Crash after DLQ acknowledgment can duplicate the DLQ record; use source-coordinate identity for deduplication. Operators replay the original protected source record through controlled Kafka tooling after correcting the cause; the application provides no unauthenticated replay endpoint.

## 5. Security and network deployment

Production Temporal uses mTLS with locally mounted client certificate, private key and trusted CA. Verify server identity and authorized namespace scope. Kafka uses `SASL_SSL` or `SSL`, trusted CA and appropriate mounted client credential; disallow insecure transport or disabled hostname verification. API ingress uses TLS and the API validates bearer issuer, audience, signature, expiration and tenant permissions. The keyring is a file mounted from enterprise-managed secret material; direct raw key environment configuration is limited to an explicit isolated development/test profile.

Certificates and keyring material must be readable by the configured non-root UID and otherwise minimally accessible. Do not commit real secrets, use build arguments for them, echo them during startup, or embed them in the image. Kubernetes Secret objects need enterprise encryption-at-rest, access controls and auditable provisioning; base64 representation is not confidentiality. The app requires neither secret-listing RBAC nor Kubernetes credentials. [Kubernetes Secret security](https://kubernetes.io/docs/concepts/configuration/secret/), [service-account token mounting](https://kubernetes.io/docs/concepts/security/service-accounts/)

Default-deny ingress/egress policies must have explicit destination/source allowances. Native NetworkPolicy does not supply portable FQDN rules; external managed services need approved stable egress gateways/address ranges or documented CNI-specific policy.

| Direction | Required allowance | Scope |
|---|---|---|
| Ingress | Ingress controller to ingestion 8080 | Only approved controller namespace/pods |
| Ingress | Prometheus to application 8080; worker SDK 9090 | Monitoring namespace/pods; no public metrics |
| Ingress | Kubelet probes | CNI/node behavior explicitly validated; do not broadly permit public callers |
| Egress | DNS TCP/UDP 53 | Approved cluster DNS only |
| Egress | Temporal TLS endpoint | Configured endpoint, typically TCP 7233 |
| Egress | Kafka bootstrap and advertised brokers | All advertised broker endpoints on approved TLS ports |
| Egress | OIDC discovery/JWKS | Approved issuer endpoint via HTTPS for ingestion |
| Egress | Telemetry collector | Approved internal OTLP/TLS collector only if tracing export enabled |
| Egress | Secret/KMS integration | Only where the chosen enterprise mechanism requires application network access; mounted keyring baseline needs none |

KEDA itself requires approved Kafka metadata/offset read permissions and Prometheus query access, separately from application policies. Namespace selectors must be combined with pod selectors where both restrictions are intended. Policies are additive and require a supporting CNI. Default-deny egress requires a separate DNS allowance. [Kubernetes NetworkPolicy semantics](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

## 6. Metrics, autoscaling and capacity qualification

Application metrics at `:8080/metrics` exist for both roles. Worker SDK/Core Prometheus metrics bind once per process to `:9090/metrics` through the shared Temporal `Runtime` before clients/workers are constructed. Ingestion does not expose the SDK exporter in this release. The implementation must not claim that application and SDK registries automatically merge. [Temporal PrometheusConfig](https://python.temporal.io/temporalio.runtime.PrometheusConfig.html)

Application counters/histograms cover API responses and start acknowledgment latency, Kafka record-to-start latency, starts/duplicates/rejections, DLQ delivery failures, bridge capacity, pending work, commit/rebalance outcomes, producer delivery outcomes, decryption failures and process health. Logs carry correlation IDs and execution context; metric labels must not carry workflow/run/message/trace IDs, tokens or payload fields. Labels are bounded to approved role, route, namespace, queue, operation, status/error code and workflow/activity type sets.

Capture SDK task schedule-to-start histograms, task slots used/available, poller health, activity execution outcomes and replay latency. Exact names, labels, prefixes and histogram units must be inspected from the pinned exporter and recorded with deployment rules; do not invent a backlog gauge or assume every SDK has every metric. [Temporal SDK metrics](https://docs.temporal.io/references/sdk-metrics)

Each autoscaled deployment has one KEDA ScaledObject and its managed HPA. Ingestion combines Kafka lag triggers for every configured topic/group binding and a Prometheus API request-rate trigger, allowing the single HPA to select the larger capacity demand. Kafka demand is bounded by assigned topic partitions when `allowIdleConsumers: false`. REST capacity may require more pods than partitions; only the documented REST-driven configuration may enable `allowIdleConsumers: true` and set the overall maximum above partition count. Additional pods have idle consumers, not more Kafka partition parallelism. A strict partition-capped profile must prove its REST SLO at that cap. [KEDA Kafka scaler](https://keda.sh/docs/2.21/scalers/apache-kafka/), [Kubernetes multiple-metric HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)

Tenant topics/groups have separate assignments, so an aggregate partition count must not be treated as one group's pod concurrency. If every pod joins all configured groups, useful consumer pods for a binding are limited by that binding's partitions. Qualify simultaneous tenant demand and shared process/API capacity across the bounded broker threads; the maximum of individually tuned lag demands can understate combined pod load. Use conservative thresholds proven under that aggregate workload, or a verified KEDA composite/Prometheus aggregate-capacity signal in the same ScaledObject. Do not create multiple HPAs to solve this. Record the chosen grouping and formula in production values and the qualification report.

Workers use Prometheus signals per namespace/capacity pool. At minimum provide capacity pressure from aggregate used task slots versus benchmarked safe per-pod capacity; use a separate scheduling-delay signal to increase demand when task latency exceeds the chosen threshold. Scheduling latency only appears for picked-up tasks and is delayed by the query window; it cannot prove that an idle worker fleet has no backlog. Two baseline replicas, worker/poller missing-series alerts and capacity metrics are therefore mandatory. Enterprise Temporal backlog metrics may improve scaling if verified and explicitly configured, but are not silently assumed to exist.

KEDA queries must return a single finite nonnegative value, select the intended deployment/namespace/queue, distinguish a healthy zero from an absent series, and set `ignoreNullValues: false` for required capacity sources. Validate real series and server access. Configure a qualified fallback replica count at least two; metric outages must not drive production below baseline. Thresholds express measured per-pod sustainable demand with headroom, not arbitrary values copied from examples. [KEDA Prometheus scaler](https://keda.sh/docs/2.21/scalers/prometheus/)

Illustrative controller values are `pollingInterval: 30`, `cooldownPeriod: 300`, `minReplicaCount: 2`, and HPA scale-down stabilization of 300 seconds. KEDA cooldown concerns scale-to-zero and does not set the 1-to-N scale-down delay. With this nonzero baseline, HPA reconciliation and metric freshness govern scaling; do not assert that pollingInterval determines all scale-up latency. No `idleReplicaCount: 0` production configuration is permitted. [KEDA ScaledObject behavior](https://keda.sh/docs/2.21/reference/scaledobject-spec/)

Qualification workload is aggregate 100 unique starts/second for 15 minutes plus a separate 300 starts/second burst for 60 seconds, across four tenants, eight trigger partitions and four routes, with 1 KiB synthetic business payloads and an approximately one-second activity. Record actual activity-duration distribution and the controlled delivery-latency/workload mechanism that creates it; business payload size does not by itself make publishing take one second. Baseline is 50% REST / 50% Kafka; run REST-only and Kafka-only variants to validate independent scaling. Each tenant has its own provisioned Temporal namespace and an assigned worker capacity pool. Declare hardware, quotas, concurrency, network latency, broker replication, TLS configuration and exporter/query windows in the report. These workloads and targets are release qualification criteria, not a blanket performance guarantee.

| Measure | Initial qualification target | Exact interval |
|---|---|---|
| API start acknowledgment | p95 <= 500 ms during steady state | Request receipt at gateway through final response after Temporal acknowledgment; includes auth/validation/start, excludes workflow execution |
| Kafka ingestion lag | p95 <= 5 seconds during steady state | Broker-acknowledged source publish through Temporal start/duplicate acknowledgment; use synchronized synthetic producer timestamps, report clock error |
| Workflow task scheduling | p95 <= 2 seconds per route/namespace in steady state | Temporal task scheduled through worker task start |
| Activity task scheduling | p95 <= 2 seconds per route/namespace in steady state | Activity task scheduled through activity task start |
| Healthy unique start success | >= 99.9% confirmed success in sustained qualification | Valid unique requests/events in the declared healthy interval; injected-failure intervals reported separately |
| Recovery/data integrity | No skipped eligible source offset; no duplicate workflow execution within contract | Source coordinate/event inventory reconciled with histories and downstream event IDs |

Measure Kafka local consume-to-start duration separately from end-to-end lag. Measure workflow completion separately from start latency. Publish p50/p95/p99, rejected/error counts, sample counts and all per-route values; do not hide a slow tenant in an aggregate percentile. Burst results must show peak lag and time to drain; initial drain target is five minutes after the burst ends without loss. Unmet targets require tuning and rerun or an explicitly revised release scope.

## 7. Rollout and incident runbooks

**Release:** render/validate configuration, verify secret/certificate access, run verification gates, record the image digest and route/key IDs without values, create a distinct immutable Worker Deployment for the candidate PINNED build, run synthetic encrypted starts and broker deliveries, then promote/ramp the candidate through qualified Temporal release controls and roll ingestion. Retain old Worker Deployments for pinned runs and recoverable histories; do not roll the candidate image over their pollers. Watch startup/readiness, nondeterminism, task latency, Kafka fences and error rates. No migration step may add a new required database. Routing changes provision compatible workers first; retire old queue pollers only after pending work and histories have a validated completion/retention path.

**Worker compatibility/rollback:** production baseline uses qualified `PINNED` Temporal Worker Versioning with immutable build identity and separately retained Worker Deployments. Change the current/ramping version for new executions through the Temporal release controls; runs already pinned to a candidate continue on its retained Deployment. A documented `COMPATIBLE_ROLLING` exception requires backward-compatible workflow code proven by replay and confirmed selected SDK/server capabilities. Never mix incompatible code on an unversioned queue. On nondeterminism, stop promotion and preserve the worker image that can replay affected histories. Redirecting new starts is not migration of existing pinned runs. Reassign or replay a run with the prior image only after proving compatible histories; otherwise retain the required version. Do not treat a Kubernetes image rollback as automatic workflow rollback.

**Kafka lag:** check source partition skew, group assignment and poll progress, blocked earliest offset, commit failures, Temporal throttling, bridge queue depth and TLS errors. Scale within qualified capacity and partition constraints. Do not reset offsets to conceal lag. Revoke/lost-partition errors are evaluated with the assignment fence; inspect generation before approving a commit. For DLQ blockage, restore DLQ availability or correct permanent validation causes; never enable auto-commit as recovery.

**Temporal outage/throttling:** retain uncommitted Kafka work, reject/defer API starts with typed retriable responses, preserve idempotency keys, and let bounded retry/backpressure prevent memory growth. Coordinate namespace quotas and server health with its owner. A client timeout is not proof of a failed start. Resume using the same ID after connectivity returns; reconcile source records against known histories.

**Worker backlog/activity failure:** distinguish task slot exhaustion, CPU-bound work blocking execution, poller/network failure, unregistered workflow type, unavailable payload key and downstream broker failure. Adding replicas cannot repair deterministic errors or missing key material. Diagnose with metadata-only logs, task scheduling and capacity metrics. Maintain old compatible pollers while repairing histories; cancel/terminate executions only through an explicitly authorized enterprise operation.

**Key rotation:** stage a keyring containing old and new keys to all ingress/worker/replay consumers; prove both keys decode; switch the active writer key; roll pods; verify cross-version histories/results; keep old decrypt keys through the longest history/archival/replay retention and operational recovery requirement. No key is retired simply because current workflows completed. Rotation uses mounted keyrings and controlled rollout; live process reload is not assumed. Security approves emergency retirement separately because undecryptable histories can halt replay.

**Certificate rotation:** overlap trust/authorization windows, mount replacement material, restart clients through controlled pod rollout, verify positive and negative TLS cases, and retire old credentials after every role/KEDA integration is confirmed. Mounted-file update does not imply a live gRPC connection reload. Alert on remaining validity with enterprise-defined lead times.

**Monitoring/scaler outage:** keep the baseline, activate qualified fallback/manual replica values through the deployment owner, and verify the single HPA owner remains intact. Restore metrics and validate a real scalar before re-enabling normal scaling. Dashboards must show scrape absence and stale series distinctly from zero.

**Recovery/disaster:** restore Temporal/Kafka through their external owners, restore the matching application image/config and complete keyring, run replay/TLS/synthetic tenant checks, then resume consumer groups at their retained committed positions. Temporal/Kafka retention and backup policies define recoverable data. This stateless application does not provide cross-system zero-loss recovery or a numerical RPO/RTO independent of those services. Record and measure agreed recovery targets in the enterprise environment.

## 8. Required operational handoff

Deliver a runbook with exact render/install/rollback commands, image and package versions, dependency owners, namespace/queue/topic map, retention boundaries, secret mount paths, network allowlists, alert routes, scaling thresholds, qualification report and test evidence IDs. Dashboards/alerts cover missing pods/pollers/scrapes, decryption failure, certificate expiry, nondeterminism, sustained start/scheduling SLO breaches, DLQ delivery failure, consumer blocked partitions, rebalance storms, Kafka lag, bridge saturation and scaler failure. Alert values are deployment configuration, not hard-coded workflow decisions.

Production approval requires all relevant [V-001 through V-030 verification gates](verification.md), including real TLS/broker/cluster tests. A unit test or local test server success alone is not a production readiness claim.
